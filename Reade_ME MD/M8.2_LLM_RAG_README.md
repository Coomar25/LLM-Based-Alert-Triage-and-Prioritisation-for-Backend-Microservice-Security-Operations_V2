# LLM+RAG Triage Pipeline — Stage 5b of the AIT-ADS Pipeline

This document is the complete reference for the **LLM+RAG triage pipeline**: the
retrieval system, the multi-provider inference layer, every design decision, the
extended infrastructure journey that got it working, and the empirical results
on the full evaluation sample.

The LLM+RAG pipeline is the **proposed system** at the heart of the
dissertation. It augments the LLM-only baseline (Stage 5a) with a retrieval
step: before the model triages an alert, relevant security knowledge (MITRE
ATT&CK techniques, CVEs, and SOC runbooks) is retrieved from the knowledge base
(Stage 4) and injected into the prompt. Comparing it against the LLM-only
pipeline — identical in every respect except the presence of retrieved context —
isolates the contribution of retrieval, which is the dissertation's central
research question.

```
Stage 1: ingest.py                ── parse raw logs into unified schema        [DONE]
Stage 2: label_alerts.py          ── apply ground-truth attack labels          [DONE]
Stage 3: run_baseline.py          ── rule-based baseline + evaluation harness  [DONE]
Stage 4: build_knowledge_base.py  ── RAG knowledge base construction           [DONE]
Stage 5a: run_llm_only.py         ── LLM-only triage (ablation baseline)        [DONE]
Stage 5b: run_llm_rag.py          ── LLM+RAG triage (proposed system)          [YOU ARE HERE]
Stage 6:  compare_pipelines.py    ── multi-way comparison                      [DONE]
```

## 1. Purpose and Research Role

The dissertation compares alert-triage approaches along a controlled progression:

1. **Rule-based** (Stage 3) — severity thresholds and correlation rules.
2. **LLM-only** (Stage 5a) — a language model reasoning over each alert with
   no external context.
3. **LLM+RAG** (this stage) — the same language model, but with relevant
   security knowledge retrieved and injected into the prompt.
4. **LLM+RAG (runbook-only)** — a retrieval-source ablation of (3), retrieving
   only from the curated runbook corpus.

The LLM+RAG pipeline exists to answer the central question: **does retrieval
improve triage, and if so, where and why?** For the comparison to be a clean
ablation, LLM+RAG must be identical to LLM-only in every respect *except* the
retrieval step:

- The same model (within any given comparison)
- The same decoding settings (temperature 0)
- The same prompt template, differing ONLY by the inserted retrieved-context
  section
- The same alerts, the same evaluation harness

Every one of these is enforced in the implementation, and a unit test asserts
that the two prompt templates differ only by the context block.

## 2. How the Pipeline Works — End to End

For each alert in the evaluation sample, the pipeline performs six steps. The
difference from the LLM-only pipeline is entirely in steps 2–3 (retrieval).

```
   ┌─────────────────────────────────────────────────────────────────┐
   │  1. Load alert (JSONL record with ground-truth labels)          │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │  2. Build a retrieval query from OBSERVABLE alert content only    │
   │     (retrieval_query_text) — rule description, rule groups,       │
   │     raw log message. NEVER the ground-truth label.               │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │  3. Retrieve relevant knowledge (source-balanced):               │
   │       - best-matching runbook   (operational "what to do")       │
   │       - best-matching MITRE technique (behavioural "what is it")  │
   │       - best-matching CVE(s)    (specific vulnerability context)  │
   │     Format as lean context for the prompt.                       │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │  4. Build the RAG prompt (build_rag_prompt): task instructions   │
   │     + few-shot examples + RETRIEVED KNOWLEDGE section + alert.    │
   │     Alert placed AFTER context (recency) so the small model       │
   │     stays anchored on the alert.                                 │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │  5. Call the model (via provider dispatch), temperature 0.       │
   │     Parse + normalise the JSON output.                          │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │  6. Record prediction against ground truth (same harness as the  │
   │     rule-based and LLM-only pipelines). Infrastructure failures   │
   │     are EXCLUDED from scoring, not counted as benign.            │
   └─────────────────────────────────────────────────────────────────┘
```

The model outputs the same JSON schema as the LLM-only pipeline:

```json
{
  "is_attack": true,
  "attack_phase": "cracking",
  "confidence": 0.85,
  "explanation": "Repeated authentication failures from a single source..."
}
```

Only `is_attack` feeds the primary binary evaluation. The retrieval metadata
(which documents were retrieved, retrieval latency, retrieval mode) is recorded
alongside for analysis.

## 3. Component Architecture

The pipeline reuses every component of the LLM-only pipeline and adds the
retrieval layer and the multi-provider inference layer.

```
ait_parser/
├── run_llm_rag.py             ← orchestrator (retrieval + concurrency + aggregation)
├── run_claude_llm_rag.py      ← same runner, Anthropic-named copy
├── run_gemini_llm_rag.py      ← same runner, Gemini-named copy
├── compare_pipelines.py       ← multi-way comparison
├── test_llm.py                ← unit tests (incl. the ablation-integrity test)
└── llm/
    ├── __init__.py
    ├── sampler.py             ← stratified sampler (shared with Stage 5a)
    ├── alert_repr.py          ← compact_alert_text + retrieval_query_text
    ├── prompts.py             ← build_rag_prompt + normalise_llm_output
    ├── retrieval.py           ← the Retriever class (source-balanced retrieval)
    ├── provider.py            ← provider dispatch (ollama/groq/gemini/anthropic)
    ├── ollama_client.py       ← local inference backend
```

Two modules are new relative to Stage 5a: `retrieval.py` (Section 4) and the

Everything else — the sampler, the alert representation, the prompt
normalisation, the evaluation harness — is shared unchanged, which is what keeps
the ablation clean.

## 4. The Retrieval System

`llm/retrieval.py` is the bridge between an incoming alert and the knowledge
base. It is the single most important piece of engineering in this stage, and it
went through two significant redesigns (Section 10).

### 4.1 The `Retriever` class

Constructed once per run with the knowledge-base directory, a `top_k`, and a
retrieval-mode flag. It wraps the ChromaDB store and the embedding model and
exposes `retrieve()` and `retrieve_and_format()`.

### 4.2 No ground-truth leakage — a correctness property

At inference time the retriever uses ONLY the alert's observable content
(description, rule groups, raw message) to build the query, via
`retrieval_query_text()`. It NEVER uses the alert's known `attack_phase` or
`is_attack` label. This is essential: if the query used the ground-truth phase,
the retrieval would be "cheating" and the comparison would be invalid. The query
builder reads only observable fields, and this is enforced by construction.

### 4.3 Source-balanced retrieval — the key design

**The problem.** The knowledge base is dominated by CVEs: 36,840 CVEs vs 697
MITRE techniques vs 8 runbooks. Naive "top-K across all sources" retrieval almost
always returns K CVEs, because they numerically overwhelm the other sources — and
often the CVEs are only loosely related (e.g. generic "web server denial of
service" CVEs retrieved for a WordPress scan). This starves the model of the
operational guidance (runbooks) and behavioural context (MITRE) that are most
useful for triage, and floods it with marginally-relevant CVE noise.

**The fix.** Source-balanced retrieval queries EACH source separately and takes
the best match from each:

- the single best-matching **runbook** (operational "what to do")
- the single best-matching **MITRE technique** (behavioural "what is this")
- the best-matching **CVE(s)** for the remaining slots (specific vulnerability
  context)

This guarantees the model always sees a runbook and a technique alongside any
CVE, rather than three loosely-related CVEs. It uses ChromaDB metadata filtering
(the `source` field) to query each source independently, de-duplicates, and
sorts the final set by ascending distance (most relevant first).

### 4.4 Runbook-only mode — the source ablation

A `runbook_only` flag restricts retrieval to the curated runbook corpus alone
(the 8 hand-authored runbooks), ignoring CVE and MITRE entirely. This exists to
answer a specific sub-question: *was the RAG benefit driven by the curated
runbooks, or by the broader corpus?* Running the pipeline with `--runbook-only`
and comparing against the full source-balanced configuration isolates the
contribution of retrieval breadth. (Result: source-balanced wins — see
Section 11 — so the broader corpus does real work.)

### 4.5 The embedder warm-up

The embedding model (`sentence-transformers/all-MiniLM-L6-v2`) is warmed once at
`Retriever` construction with a dummy embed call. This matters because the model
otherwise lazy-loads on the first real retrieval, adding a ~5-second one-time
cost *inside* the timed inference loop. Warming it at construction moves that
cost out of the measurement. After warm-up, per-alert retrieval runs in roughly
80–240 ms (see the `mean_retrieval_ms` field in results).

### 4.6 Thread-safety

The RAG pipeline calls `retrieve()` from multiple worker threads. Retrieval is
guarded by a lock. Since retrieval (embedding + a few ChromaDB queries) is fast
relative to the LLM call, the lock has negligible throughput impact while
eliminating any risk of a race in the underlying libraries.

## 5. The Multi-Provider Inference Layer

The single biggest engineering effort in this stage was **not** the retrieval —
it was getting a working, fast, reliable inference backend. The pipeline
supports four interchangeable backends behind a uniform interface. The story of
*why* there are four is told in Section 10; this section documents *how* the
layer works.

### 5.1 The uniform interface

Every backend exposes the same two functions:

- `generate(prompt, model, ...) -> LlmResponse`
- a health check (`check_ollama`, `check_groq`, `check_gemini`,
  `check_anthropic`)

And every backend returns the same dataclass:

```python
@dataclass
class LlmResponse:
    raw_text: str
    latency_ms: float
    parsed_json: Optional[dict]
    parse_ok: bool
    error: Optional[str] = None
    infra_error: bool = False    # ← critical, see 5.3
```

Because the interface is identical, the runners are model-agnostic: swapping
backends is a one-argument change (`--provider`).

### 5.2 The provider dispatch

`llm/provider.py` maps a provider name to the right client and wraps it in a
uniform `Provider` object with `generate()` and `check()` methods. The runners
call `get_provider(args.provider, model=args.model)` and then use
`provider.generate(prompt)` — they never touch a specific client directly. Adding
a new backend is: write a client with the standard interface, add one branch to
`get_provider`, add the name to the `--provider` choices.

### 5.3 `infra_error` — the correctness fix that matters most

This flag is the most important detail in the whole inference layer. It
distinguishes two fundamentally different failure modes:

- **`parse_ok=False, infra_error=False`** — the model answered, but the JSON
  didn't parse. This is a genuine model failure and is counted (as a malformed
  output, defaulting to benign).
- **`infra_error=True`** — we never got a usable answer at all (rate-limit,
  timeout, empty response after all retries, auth failure). This is an
  infrastructure failure and is **EXCLUDED from scoring**, not counted as a
  (benign) prediction.

Why this matters: without the distinction, a rate-limited call returns an empty
response, which the normaliser defaults to "benign", which is then scored as a
missed attack. On a throttled run this silently manufactures hundreds of phantom
false-negatives and destroys recall — producing a comparison that looks
meaningful but is entirely corrupt. The `infra_error` flag, and the runner logic
that excludes such alerts (tracked as `infra_failed_excluded`), is what makes the
results trustworthy. This is discussed in detail in Section 10.

### 5.4 The four backends

| Backend | Model used | Free? | Role in the project |
|---|---|---|---|
| **Ollama** (local) | llama3.1:8b | Yes | Resource-constrained on-prem validation; always works, but slow (~66 s/alert on CPU) |
| **Groq** | llama-3.1-8b-instant | Free tier | Attempted for speed; free-tier rate limits corrupted runs |
| **Gemini** | gemini-2.0-flash | Free tier | Attempted; empty responses + rate limits |
| **Anthropic** | claude-haiku-4-5 | Paid | The backend that worked: full 3,500-alert run in ~57 min, clean |

Each hosted client handles rate limiting with capped exponential backoff, flags
exhausted retries as `infra_error`, and (for Anthropic) forces clean JSON via
assistant-prefill. The Anthropic client additionally treats 429/quota/billing
rejections as `infra_error` so a mid-run quota wall never corrupts the metrics.

## 6. Design Decisions

### 6.1 The RAG prompt differs from the LLM-only prompt by ONLY the context block

**Decision.** `build_rag_prompt` shares a character-identical task-instruction
block and few-shot set with `build_llm_only_prompt`; it inserts a "RETRIEVED
SECURITY KNOWLEDGE" section and nothing else.

**Rationale.** This is what makes the comparison a clean ablation. If the two
prompts differed in wording, tone, or instructions, any performance difference
could be attributed to the prompt rather than to retrieval. A unit test asserts
the shared block is identical between the two builders.

### 6.2 The alert is placed AFTER the retrieved context

**Decision.** In the RAG prompt, the retrieved context comes first, then the
alert, then the "JSON response:" cue.

**Rationale.** Language models attend most strongly to what is nearest the
generation point (a recency effect). Placing the alert last keeps the model
anchored on the alert being triaged, treating the retrieved context as reference
material rather than letting it dominate. This was particularly important for
smaller models, which are more easily distracted by long context.

### 6.3 The prompt warns that retrieved context may be irrelevant

**Decision.** The RAG context section is introduced with an explicit note that
retrieved entries may be only loosely related and should be used only where they
genuinely apply.

**Rationale.** Retrieval is imperfect — sometimes it returns marginally-relevant
documents. Instructing the model to treat context critically, rather than
assuming everything retrieved is authoritative, reduces the risk of noisy
context degrading the decision. This instruction lives only in the RAG-specific
section, so it does not affect the LLM-only baseline and the ablation stays
clean.

### 6.4 Source-balanced retrieval over pure top-k

Documented in Section 4.3. The decision was driven directly by observed
retrieval failures (Section 10.2).

### 6.5 Infrastructure failures are excluded, not counted

Documented in Section 5.3. The decision was driven directly by the rate-limit
corruption discovered on the hosted backends (Section 10.4).

  recommended pattern is `export` in `~/.bashrc` (outside the repo, so the key
  cannot be committed).

## 8. How to Run It — Step by Step

From the project root:

### Step 1: Build the evaluation sample (shared with Stage 5a)

```bash
python3 ait_parser/llm/sampler.py \
    --input data/processed/alerts_labeled.jsonl \
    --output data/processed/sample_3500.jsonl \
    --profile medium --seed 42
```

The SAME sample file is used for LLM-only and both RAG configurations, so all
approaches are evaluated on identical alerts.

### Step 2: Smoke test (10 alerts)

Validate that retrieval loads, the backend responds, and JSON parses:

```bash
python3 ait_parser/run_llm_rag.py \
    --input data/processed/sample_3500.jsonl \
    --output results/rag_smoke \
    --kb-dir data/kb \
    --provider anthropic --model claude-haiku-4-5-20251001 \
    --workers 2 --top-k 3 --limit 10
```

Confirm `malformed_outputs: 0` and `infra_failed_excluded: 0` before a full run.

### Step 3: Full run — source-balanced RAG

```bash
python3 ait_parser/run_llm_rag.py \
    --input data/processed/sample_3500.jsonl \
    --output results/llm_rag_claude_3500 \
    --kb-dir data/kb \
    --provider anthropic --model claude-haiku-4-5-20251001 \
    --workers 2 --top-k 3
```

### Step 4: Full run — runbook-only RAG (the source ablation)

```bash
python3 ait_parser/run_llm_rag.py \
    --input data/processed/sample_3500.jsonl \
    --output results/llm_rag_claude_3500_runbook \
    --kb-dir data/kb \
    --provider anthropic --model claude-haiku-4-5-20251001 \
    --workers 2 --top-k 1 --runbook-only
```

### Step 5: Compare

```bash
python3 ait_parser/compare_pipelines.py \
    --llm-only results/llm_only_claude_3500/results.json \
    --llm-rag results/llm_rag_claude_3500/results.json \
    --output results/comparison_claude_3500
```

**Note on `--workers`:** use `--workers 2` on hosted backends to stay under
free/entry-tier rate limits. Higher concurrency triggered throttling that, before
the `infra_error` fix, corrupted results (Section 10).

## 9. Outputs

Each run produces two files in its output directory.

### 9.1 `predictions.jsonl`

One record per alert, including retrieval metadata:

```json
{
  "alert_id": "...",
  "scenario": "wheeler",
  "actual_is_attack": true,
  "actual_attack_phase": "cracking",
  "predicted_is_attack": true,
  "predicted_attack_phase": "cracking",
  "confidence": 0.85,
  "explanation": "...",
  "retrieval_ms": 236.3,
  "latency_ms": 2127.9,
  "parse_ok": true,
  "infra_error": false
}
```

### 9.2 `results.json`

The aggregate metrics (overall, per-scenario, per-phase), plus RAG-specific
fields: `top_k`, `retrieval_mode` (`source_balanced` or `runbook_only`),
`mean_retrieval_ms`, `kb_document_count`, `malformed_outputs`,
`infra_failed_excluded`, `provider`, and `model`.

**Always check `infra_failed_excluded` before trusting a result.** Near zero
means the metrics are computed on essentially the full sample. A high value means
the run was throttled and the metrics, while not corrupted, are computed on fewer
alerts.

## 10. The Infrastructure Journey

This stage's implementation was dominated by an extended battle to obtain a
working inference backend. The journey is documented here because the fixes
explain the final architecture, and because the central bug (rate-limit
corruption) is a genuine methodological cautionary tale worth reporting.

### 10.1 Local inference works but is too slow

Local Ollama with Llama 3.1 8B produces clean, valid results — but at ~66
seconds per alert on CPU (no GPU available). A full run of three pipelines over
several thousand alerts would take days. This motivated the search for a faster
hosted backend, and hence the multi-provider architecture.

### 10.2 The retrieval-quality redesign

Early RAG runs collapsed to all-benign. Inspecting the retrieved context for a
WordPress-scan alert revealed the cause: retrieval returned three irrelevant
embedded-web-server denial-of-service CVEs (NicheStack, CODESYS, MiniWeb), while
the relevant WordPress runbook never surfaced — because 36,840 CVEs numerically
drown 8 runbooks under pure top-k similarity. The noisy context actively pushed
the model toward "benign". **Fix:** source-balanced retrieval (Section 4.3),
which guarantees a runbook and a MITRE technique are always retrieved alongside
CVEs. A second issue — the embedding model reloading on every call — was fixed
with the construction-time warm-up (Section 4.5).

### 10.3 Groq: rate-limited into corruption, then Cloudflare-blocked

Groq offered fast inference on the same Llama 8B family. But full runs showed
56–85% "malformed" outputs and wall-clock times of 8–15 hours (versus ~10 minutes
expected). **Root cause:** the free tier throttled nearly every call; throttled
calls returned empty bodies that the normaliser defaulted to benign, and
hundreds of real attacks became phantom false-negatives. The resulting
comparison was entirely invalid. Separately, sustained request bursts tripped
Cloudflare's bot protection (HTTP 403, error 1010), which a User-Agent header
partially mitigated. The decisive problem was throughput: even with fixes, the
free tier could not sustain thousands of calls in reasonable time.

### 10.4 The `infra_error` fix — the methodological turning point

The Groq experience exposed a latent flaw in the pipeline itself: it could not
tell an infrastructure failure from a genuine benign prediction. The fix was to
add the `infra_error` flag (Section 5.3) to every client and to make the runners
**exclude** infra-failed alerts from scoring (tracking them as
`infra_failed_excluded`) rather than counting them as benign. This is what makes
every subsequent result trustworthy: a throttled run now produces honestly
smaller-N metrics with a visible exclusion count, never silently corrupted
metrics.

### 10.5 Gemini: empty responses and throttling

Google Gemini (different infrastructure, no Cloudflare layer) was tried next. Its
free tier returned empty responses from the start and then began rate-limiting
partway through a run. With the `infra_error` fix in place these failures were at
least honestly excluded rather than corrupting the metrics — but the run still
could not complete cleanly.

### 10.6 Anthropic Claude Haiku — the backend that worked

The Anthropic API (paid, per-token) ran on reliable infrastructure with generous
rate limits. Two wrinkles were resolved:

- A first full run (`--workers 4`) hit a rate/quota wall at ~70% of the way
  through; the final ~1,244 calls returned empty and — because those failures were
  not yet flagged as infra — were miscounted, of which 855 were real attacks. This
  was traced by inspecting the predictions (empty output, 0 ms latency, clustered
  entirely in the last 30% of the run — the signature of a quota wall, not a JSON
  problem). **Fix:** treat 429/quota/billing rejections as `infra_error`, and
  re-run at `--workers 2` to stay under the rate limit.
- Claude has no "force JSON" API flag; the client uses **assistant-prefill**
  (seeding the reply with `{`) to force clean JSON, then prepends the brace back
  before parsing.

The re-run at `--workers 2` completed the full 3,500-alert sample cleanly: zero
malformed, zero infra failures, all alerts scored. This is the reportable result.

### 10.7 Lessons for the dissertation

- **Silent defaulting is dangerous.** A pipeline that maps failures to a valid
  class (benign) will manufacture corrupt results under infrastructure stress.
  Distinguishing "no answer" from "answered X" is essential.
- **Free-tier hosted inference does not scale** to thousands of calls; either
  local inference (slow but free and reliable) or paid inference (fast and
  reliable) is required for research volumes.
- **Retrieval quality, not retrieval presence, determines RAG's value** —
  documented empirically in the retrieval redesign and the source ablation.

## 11. Empirical Results

All results on the 3,500-alert stratified sample (test split only), Claude Haiku
4.5, `--workers 2`. Both RAG runs: zero malformed, zero infra failures, all
scored.

### 11.1 Overall metrics (LLM-only vs the two RAG configurations)

```
                          Precision   Recall    F1      FPR
LLM-only                    0.954     0.470   0.630   0.057
LLM+RAG (source-balanced)   0.936     0.528   0.675   0.091
LLM+RAG (runbook-only)      0.918     0.499   0.646   0.111
```

**Source-balanced RAG improved recall (+5.8 pts) and F1 (+4.5 pts)** over the
LLM-only baseline, at a small precision cost and a modest FPR rise. The
comparison tool reports **8 phases improved, 0 worsened**.

### 11.2 Per-phase recall — where RAG helped

| Phase | LLM-only | Runbook-only | Source-balanced |
|---|---|---|---|
| wpscan | 1.000 | 1.000 | 1.000 |
| dirb | 0.981 | 0.967 | 0.986 |
| service_scans | 0.576 | 0.528 | 0.597 |
| service_stop | 0.571 | 0.571 | 0.571 |
| privilege_escalation | 0.320 | 0.344 | 0.328 |
| reverse_shell | 0.258 | 0.303 | 0.288 |
| **webshell** | 0.118 | 0.265 | **0.279** |
| **cracking** | 0.019 | 0.111 | **0.175** |
| **dnsteal** | 0.011 | 0.122 | **0.147** |
| **network_scans** | 0.010 | 0.028 | **0.072** |

The gains are concentrated on the knowledge-dependent phases (cracking ×9,
dnsteal ×13, network_scans ×7, webshell ×2.4), while the text-self-evident phases
(wpscan, dirb) are unchanged — retrieval adds nothing where the signal is already
in the raw log.

### 11.3 Source-balanced vs runbook-only

Source-balanced beats runbook-only on recall (0.528 vs 0.499), F1 (0.675 vs
0.646), AND precision (0.936 vs 0.918). So the broader corpus (MITRE + CVE
alongside runbooks) does real work — the curated runbooks alone capture only part
of the benefit. Retrieval **diversity** matters.

### 11.4 Retrieval latency

`mean_retrieval_ms` was ~80 ms (runbook-only, top-1) to ~236 ms (source-balanced,
top-3) — negligible relative to the ~2,100 ms model call, confirming the
warm-up fix worked.

## 12. Interpretation and Dissertation Implications

### 12.1 The central finding

On a clean, full-scale run, **RAG improves LLM alert triage**, and the
improvement is concentrated exactly where the LLM-only baseline was weakest — the
attacks that require domain knowledge to recognise (cracking, DNS exfiltration,
scanning). This is the mechanism the dissertation predicted: retrieval supplies
the security knowledge the model lacks, and only where it is needed.

### 12.2 The retrieval-diversity sub-finding

The source ablation (source-balanced vs runbook-only) shows that retrieval
*breadth* matters: the full knowledge base outperforms the curated runbooks
alone. This is a specific, defensible design insight — naive single-source
retrieval leaves performance on the table.

### 12.3 The honest trade-off

RAG raised the false-positive rate (0.057 → 0.091). Framed against the
alert-fatigue motivation, this is a favourable trade: recovering missed attacks
(higher recall) at a false-positive rate still an order of magnitude below the
rule-based baselines. Whether the trade is worthwhile depends on the SOC's
priorities, but for most operations a missed cracking or exfiltration attack is
costlier than one additional false positive to review.

### 12.4 Relation to the earlier small-sample result

An earlier comparison on a 129-alert local run with Llama 8B had suggested RAG
*degraded* recall. The clean 3,500-alert run reverses this. The discrepancy is
attributable to sample size and (in the interim cloud attempts) rate-limit
corruption. The reportable finding is the clean, full-scale one; the earlier
small/corrupted runs are documented for transparency but are not the result.

## 13. Known Limitations

- **Model family differs from the local baseline.** The full-scale results use
  Claude Haiku 4.5, a different model from the local Llama 8B. The RAG ablation
  is valid because both arms use the same model, but absolute numbers would
  differ with another model. The two backends are framed as two deployment modes
  (on-prem vs hosted).
- **Cost.** Hosted inference is paid; the experimental runs cost a few dollars
  each. This is a real deployment consideration and is disclosed.
- **Single-alert context.** Each alert is triaged in isolation; the pipeline
  cannot see multi-alert attack patterns. Shared with the other pipelines for
  fair comparison, but it limits achievable recall on volume-based phases.
- **Retrieval is single-shot.** One retrieval per alert, no iterative or agentic
  retrieval. Noted as future work.
- **Rare-phase sample sizes.** service_stop (n=7) and other rare phases have
  small counts; their per-phase figures are indicative rather than precise.
